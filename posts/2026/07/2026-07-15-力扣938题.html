力扣938题

2026-07-15

前言

这题是力扣938.二叉搜索树的范围和，题目本身并不难解决，用简单的递归便可以解决，起初采用的是按照中序排序的方法进行简单递归:


class Solution {
public:
    int rangeSumBST(TreeNode* root, int low, int high) {
        int ans = 0;
        if(!root)return 0;
        ans += rangeSumBST(root -> left, low, high);
        if(root -> val >= low && root -> val <= high) ans += root ->val;
        ans += rangeSumBST(root -> right, low, high);
        return ans;
    }
};

然而这种方法的效率远低于前序遍历的版本:


class Solution {
public:
    int rangeSumBST(TreeNode* root, int low, int high) {
        if(root==nullptr) return 0;
        TreeNode* cur=root;
        int ans=0;
        if(cur->val>=low&&cur->val<=high) ans+=cur->val;
        return ans+rangeSumBST(cur->left,low,high)+rangeSumBST(cur->right,low,high);
    }
    
};

经过验证为编译器处理算法过程中优化的差异导致的(通常为常数级别的差异)，下面我们将学习编译器对不同算法的反应。

分析

中间变量的修改次数不同

前一种方法ans累加左子树结果、根节点值、右子树结果。ans在整个函数期间多次读写。

而后一种方法只对ans赋值1次，减少了对同一变量的反复修改。

这种写法更容易被编译器优化成高效的指令序列，减少不必要的内存操作。

表达式求值

后一个代码返回一个完整的加法表达式，编译器在生成代码时可以更灵活地安排递归调用和加法指令，而前一个代码强制顺序执行，不利于指令级并行。

原则

虽然只影响常数级别的复杂度，但还是尽量写出清晰简单的代码，以便编译器生成更优秀的机器码。

下面是一些基本原则:

1. 写清楚数据依赖，避免不必要的中间变量修改

编译器喜欢：每个值的“生产—消费”关系简单，一条线到底。不喜欢：同一个变量反复赋值，形成复杂的写后读、读后写链条，这会限制寄存器复用和指令重排。

不好的写法（多次修改 ans）

int ans = 0;
ans += left_sum;
ans += root_val;
ans += right_sum;
return ans;

好的写法（直接构造返回值）


return left_sum + root_val + right_sum;

后者让编译器看到加法是可以多项并列执行的，它能更好地分配寄存器、并行计算。

2. 用局部变量缓存频繁访问的全局/成员数据

编译器受别名分析限制，如果它不确定某个内存位置会不会在函数调用或赋值中改变，就不会把值缓存在寄存器里，而是反复从内存读取。你主动拷贝到局部变量，相当于告诉编译器“这个值不会变”，它就能安心优化。

例子：

// 不信任编译器能优化掉重复读取 global_val
if (global_val > 0 && global_val < 100) ...

// 更好：用局部副本
int val = global_val;
if (val > 0 && val < 100) ...

特别是对全局变量、类成员变量，在非简单场景下这么做很有好处。

3. 减少对于指针/引用的过度解引用

即使你用局部引用，编译器可能仍需处理别名问题。如果确定数据不会被意外修改，可以用 const 修饰，或直接取副本。

更好：

void foo(const std::vector<int>& v) {
    for (size_t i = 0, n = v.size(); i < n; ++i) {
        int x = v[i];    // 如果后面多次使用 x，可以缓存
        ...
    }
}

如果 v 随时可能被外部修改（哪怕不是本函数）编译器就得多次读内存，用局部变量 x 避免重复 v[i]。

4. 优先使用简单的返回值形式，避免通过参数返回

不好（通过非 const 引用输出结果）

void compute(int a, int b, int& result) {
    result = a + b;
}

好（直接返回）

int compute(int a, int b) {
    return a + b;
}

直接返回不仅清晰，还支持返回值优化（RVO），甚至能被尾调用优化。对编译器来说，纯函数的分析也比有副作用的函数简单很多。

5. 用常量、const 给编译器更多信息

能加 const 就加（变量、函数参数、成员函数），告诉编译器“这个值不会变”，它就可以做常量传播、死代码消除等优化。用 constexpr 让编译期计算出结果，完全消除运行时开销。

const int size = 1024;          // 明确常量
constexpr double pi = 3.14159;  // 编译期计算

6. 让循环结构清晰，减少分支

把不变量的计算提到循环外。使用 for (auto&& item : container) 等现代写法，让迭代器操作内联优化。如果循环内有条件判断，考虑是否可以拆成两个循环，或者用无分支的方式（如位运算）处理，避免分支预测失败。

不好（条件在循环内，且条件不变）

for (int i = 0; i < n; ++i) {
    if (flag) {
        doA(i);
    } else {
        doB(i);
    }
}

如果 flag 是外部传入不变，可以：

if (flag) {
    for (int i = 0; i < n; ++i) doA(i);
} else {
    for (int i = 0; i < n; ++i) doB(i);
}

减少每次循环检查 flag，也利于向量化。

7. 善用标准库和现成的算法

标准库函数通常是专家精调过的，内部做了许多微优化，并且编译器对内建函数和常见模式有特殊处理。比如用 std::copy、std::fill 可能比自己写的循环更容易触发 SIMD 指令。

8. 函数短小精悍，让内联更容易

编译器对短函数更愿意内联，内联后很多跨语句的优化（常数折叠、死代码消除）才能发生。避免写巨大无比函数，职责单一，长度通常不超过几十行。

9. 如果是递归，尝试写成尾递归形式（哪怕语言不保证）

尾递归的形式：

return func(...);

不处理返回值，只是直接返回调用结果。编译器可以优化成循环，减少栈使用。日常写递归时，如果最后一步是调用自身并直接返回，就写成一个单一的 return 语句，不要暂存到变量再返回。

10. 减少临时对象与不必要的拷贝

用移动语义（std::move）或完美转发减少深拷贝。对于传入的大对象，用 const &，返回时如果必须构造新对象，直接返回表达式，依靠 RVO / NRVO 避免额外拷贝。

不好：

std::string make() {
    std::string tmp = ...;
    return tmp; // 可能拷贝（不过现代编译器会优化，但写法仍不直接）
}

好：

std::string make() {
    return std::string(...); // 保证 RVO
}

总结：编译器喜欢的代码长这样

  • 数据流：一次赋值、直接返回，少改局部变量。
  • 别名：用局部副本隔离全局/成员，减少解引用。
  • 分支：顺序执行，少跳转，条件提前判断（如 guard clause）。
  • 函数：短小、纯函数、多返回值少副作用。
  • 信息：多用 const / constexpr。
  • 循环：不变量外提，少条件内联。
  • 尾调用：递归直接 return 自身调用。
