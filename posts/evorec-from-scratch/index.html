从零构建 EvoRec：一个推荐算法项目的持续实践记录

2026-09-15 · 日志更新至 2026-10-08

记录从选题、方案设计、算法实验到系统展示的完整过程。

当前阶段：R01–R06 离线实验已归档。R06 在相同候选预算下比较多兴趣召回，覆盖略增，但区间跨过零，没有证据支持替换原路径。本地单实例演示已接通会话、反馈、新品内容基线、策略对比和可选的冻结 R06 服务；R06 默认关闭，不能把任意新商品放进旧模型。

一、项目背景与目标

这个项目源于我从 C++ 后端开发向推荐算法领域转型的学习需求。相比单纯阅读论文或跑通开源代码，我希望通过构建一个完整的推荐系统来理解算法背后的工程实现、实验设计和问题权衡。

为什么选择推荐系统

推荐系统是一个既有理论深度又有工程复杂度的领域。它涉及机器学习、信息检索、系统设计等多个方面，同时也有明确的业务价值和评估标准。选择“动态商品库推荐”这个场景，是因为它包含了推荐系统中最核心的挑战：

  • 冷启动问题：新商品没有历史交互数据，如何快速让它们参与推荐？
  • 实时性要求：商品库不断更新，系统需要快速响应新品入库。
  • 多路召回融合：需要平衡协同过滤、内容检索等多种策略。
  • 效果可验证：有清晰的离线评估指标和在线业务指标。

项目目标

通过这个项目，我希望实现以下几个目标：

  • 技术能力：掌握 Python/PyTorch 推荐算法实现，理解序列推荐、双塔模型等经典方法。
  • 工程能力：构建完整的推荐服务，包括数据处理、模型训练、在线服务和前端展示。
  • 实验方法：学会设计实验、选择基线、分析结果、定位问题。
  • 可交付成果：一个可演示的推荐系统，包括算法模块、API 服务和前端界面。

离线实验已推进到 R06。工程侧已有本地持久化演示：会话与反馈写入 PostgreSQL，商品导入、后台构建和发布可以在单实例上操作。页面是零构建的本地 Web，不是最初设想的 React 应用。冻结 R06 服务要显式启用、批准并发布；新品走独立内容基线。持续负载、多 worker 租约和公网身份仍未验收。仓库当前 HEAD 为 6fd93ba。

二、核心问题与解决思路

问题场景

考虑一个典型的电商推荐场景：每天都有新商品上架，这些新商品没有任何历史交互数据。如果使用纯协同过滤方法，这些商品永远不会被推荐给用户，因为它们不在模型的"词表"中。但对商家来说，新品的曝光至关重要；对用户来说，新品可能正是他们感兴趣的。

这就是推荐系统中的"冷启动"问题。EvoRec 项目专注于解决这个问题，同时保持整体推荐质量。

技术挑战

  • 冷商品可达性：没有交互历史的商品如何进入候选集？
  • 多路召回融合：如何平衡协同过滤（基于用户行为）和内容检索（基于商品特征）？
  • 动态策略调整：针对不同用户（新用户 vs 活跃用户），应该采用什么样的召回策略？
  • 排序优化：如何在排序阶段提升冷商品的曝光，而不损害整体效果？

系统目标

EvoRec 的最终目标是构建一个完整的可演示系统，包括：

  • 推荐服务：支持实时推荐请求，处理用户反馈（收藏、屏蔽等）。
  • 商品管理：支持新品入库、编码、索引构建和发布。
  • 策略对比：可视化展示不同策略的效果差异。
  • 效果看板：实时监控推荐质量和冷商品曝光率。

这四项里，推荐、反馈、新品发布和策略对比已经能在本地单实例上操作。效果看板没有做成线上监控；现有的是结果页上的离线档案，以及评估工作台里按冻结配置重算的指标。成功标准不仅是功能完成，更重要的是实验可信、结果可追溯。没有对照的改动不写成提升。

三、技术选型与架构设计

技术栈选择

在明确了问题和目标后，我需要选择合适的技术栈。考虑到学习曲线、生态成熟度和社区支持，最终选择了以下技术组合：

  • 算法框架：Python + PyTorch — 推荐算法领域的主流选择，有丰富的预训练模型和工具库。
  • 向量检索：Faiss — Facebook 开源的高性能相似度搜索库，支持多种索引类型。
  • 数据存储：PostgreSQL — 可靠的关系数据库，支持事务和复杂查询。
  • API 服务：FastAPI — 现代 Python Web 框架，自动生成文档，异步支持好。
  • 前端展示：最初计划用 React。实际落地的是零构建本地页面，由 FastAPI 提供 /app，不单独做前端构建。

架构设计原则

在设计系统架构时，我遵循以下原则：

  • 模块解耦：算法、数据、服务和展示模块独立开发和测试。
  • 契约优先：先定义接口和数据格式，再实现具体逻辑。
  • 版本管理：模型、编码器、索引作为一个 bundle 统一版本。
  • 可测试性：关键路径有自动化检查，使用测试替身隔离依赖。

关于 C++ 的考虑

作为 C++ 背景的开发者，我最初考虑在性能关键路径使用 C++。但经过权衡后决定：

  • 先用 Python 验证：在明确瓶颈之前，不引入额外复杂度。
  • 保留优化空间：如果后续测量发现性能问题，可以用 pybind11 封装 C++ 扩展。
  • 利用现有工具：Faiss 本身就是 C++ 实现，通过 Python 绑定使用即可。

这个决策让离线实验先跑起来。到 2026-10 测量 R06 服务路径之后，在线实现仍然是 Python。可选的 NumPy 分块只加速冻结内容召回这一段，cpp/ 仍是接入条件，没有换成 pybind11。

四、工程框架搭建

设计原则

在开始编码之前，我花了相当多时间思考工程组织。一个好的框架应该：

  • 契约先行：先定义接口和数据格式，模块之间通过契约通信。
  • 可测试性：核心逻辑独立于外部依赖，可以用测试替身验证。
  • 版本一致性：模型、编码器和索引作为一个 bundle 统一管理。
  • 清晰的状态转换：区分“服务启动”和“推荐就绪”，明确商品的生命周期。

核心模块

  • domain/ — 不可变请求快照和合法推荐规则，不依赖具体数据库。
  • application/ — 推荐编排、就绪查询和依赖接口。
  • infrastructure/ — 内存后端、PostgreSQL、冻结模型和目录适配。
  • api/ — FastAPI 的会话、推荐、反馈和管理路由。
  • research/ — 离线采样、训练和评价。服务默认不加载研究模型。
  • web/ — 本地推荐页、商品工作台、结果页和评估页。

当前实际进展

早期框架只证明契约和应用层边界：FastAPI 骨架、请求绑定和用测试替身隔开的检查。那一轮约 55 项自动检查不能说明推荐效果或数据库事务已经成立。

到 2026-10-08，同一套服务已经能做这些事：

  • 创建带访问令牌的会话，执行推荐，并用 event_id 幂等记录收藏、隐藏和撤销。配置 EVOREC_DATABASE_URL 后，会话、请求和结果写入 PostgreSQL；不配置时仍可用进程内后端。
  • 管理端导入商品、排队构建标题和类别内容基线、预览、确认发布、下架和守卫回滚。构建由独立的 catalog_worker 消费，只启动 API 时任务保持排队。
  • 策略对比和批量快照评估各有自己的 worker 与页面。它们的结果与普通推荐记录分开存放。
  • 冻结 R06 包可以显式启用、批准准备并发布。默认关闭。新品走独立内容基线，最多 5,000 件，不能把任意新 ID 放进旧模型。

重要说明：服务测试通过，只说明这条本地路径按约定工作。推荐质量仍以第五节的离线实验为准。R06 在原 2 秒期限下的完整包请求曾经超时，并发负载里仍有 504，不能把演示能点开写成吞吐已经达标。

五、第二阶段：准备数据与建立基线

  • 数据从哪里来，包含哪些字段。
  • 如何清洗交互、统一商品 ID 和处理缺失数据。
  • 如何划分训练、验证和测试数据。
  • 怎样避免未来信息进入训练或评估。
  • “模型冷物品”和“刚刚发布的新品”有什么区别。
  • 首次跑通的基线、使用的设备、资源消耗与结果。

R01 已完成。 从官方 Video_Games 交互文件读取前 50,000 条，得到 20,375 个用户和 18,508 件商品；在 2,291 个测试正反馈上，热门推荐 NDCG@10 为 0.007388，ItemCF 为 0.004636。共有 79 项检查通过，9,852 条逐请求结果完成独立核对。前缀样本中 1,101 个测试目标在请求时尚未被观察到，保留在主指标分母中。

R02 已完成。 完整扫描 4,555,500 条交互，按固定用户哈希保留约二十分之一用户的全部记录，得到 226,172 条交互和 137,103 个用户。GPU 自注意力序列模型完成 4 次训练、39 个 epoch 和三个种子运行；测试 NDCG@10 为热门 0.004755、时间衰减协同融合 0.008380、序列模型均值 0.005628 ± 0.000222。序列模型超过历史热门，但没有超过更强的时间衰减基线。

本轮还发现 6,874 个模型冷且可用目标全部未命中。没有商品表示入口时，继续增加 Transformer 训练轮数无法让新商品进入词表；下一步先补内容候选路径，并登记新的评价窗口。

R03 已完成。 引入内容双塔架构，使用商品标题、品牌和类别进行语义编码。完成 48 个 epoch 训练，构建协同过滤与内容检索的混合召回策略。内容融合改善整体排序性能，但冷商品命中率仍低于预期。

R04 已完成。 冻结 R03 模型，设计冷商品保留与门控策略。通过验证集比较五种预登记策略，分析冷商品在各检索阶段的落选位置。门控机制根据历史信号动态调整召回路径，在不跳过任何检索通道的前提下提升冷商品曝光。

2026-09-24 的研究索引把这一轮改记为：冷商品保留和规则门控未获验证集支持，留下的是落选位置。上面这句话和 09-16 日志保留当时的写法；是否构成曝光提升，以仓库 R04 报告为准。

R05 已完成。 引入新排序模型 ColdListMLP，针对冷样本进行加权训练。完成 35 轮训练，在相同候选池下与普通 ListMLP 进行对比。冷样本加权策略在保持整体性能的同时提升冷商品排序效果。

R06 已完成，但没有证据支持替换原路径。 测试用户与 R01–R05 的交集为零，共 12,524 个正反馈请求、9,373 名用户。比较的是相同候选数量预算下的均值内容召回和近期多兴趣召回。验证规则保留 A-frozen-s17，本轮没有换路径。

六、第三阶段：理解与实现推荐方法

  • 从简单基线开始，逐步理解序列推荐与内容检索。
  • 如何阅读 TIGER、LIGER 等相关工作。
  • 商品内容向量、语义 ID 和用户表示分别是什么。
  • 新商品加入后，各条检索路径如何处理。
  • 为什么提出预算路由，以及它依赖哪些信息。
  • 论文实现与统一实验协议之间有哪些差异。

实际走过的方法是这几条，不是论文复现清单。

  • 统计基线：热门和 ItemCF 用来确认时间回放本身能跑通。R02 里更强的对照是时间衰减协同融合，序列模型没有超过它。
  • 序列模型：自注意力序列模型按用户历史预测下一个商品。它只能推荐训练词表里的 ID。R02 的 6,874 个模型冷目标全部未命中，说明继续加训练轮数解决不了新品。
  • 内容双塔：用标题、品牌和类别做语义向量，让没有交互的商品也能进入候选。R03 的内容融合改善了整体排序，冷商品命中仍低于纯内容路径。
  • 门控与冷排序：R04 在冻结的 R03 模型上比较五种预登记策略，并记录冷商品在哪一段落选。后来的研究索引不把门控当成已获验证集支持的提升。R05 在同一候选池里比较普通 ListMLP 和冷样本加权的 ColdListMLP。
  • 多兴趣召回：R06 在相同候选数量下，把近期多个兴趣和均值内容向量对照。覆盖略增，排序差值的区间跨过零，所以服务默认仍走原来的冻结路径，而不是自动换成多兴趣。

预算路由和生成式语义 ID 没有做统一对照。TIGER、LIGER 仍只作为阅读背景，没有对应的实验协议。

七、第四阶段：用实验检验想法

  • 实验要验证的假设是什么。
  • 为什么选择这些基线与评价指标。
  • 如何比较整体、冷物品和低频物品表现。
  • 如何保证不同方法的候选范围和计算预算可比。
  • 消融实验如何判断每个模块的作用。
  • 哪些实验没有提升，可能原因是什么。
  • 哪些观察可以形成结论，哪些还需要更多证据。

对照时固定这几件事：用户按哈希划分，测试请求不能看到未来交互；冷目标是训练时没出现过的商品，无历史冷目标又是其中完全没有可建模行为的一部分；不同方法要在同一候选数量预算下比，不能一边多召回一边声称排序更好。R06 把这三条都写进了预登记。结果是覆盖从 115 增到 122，无历史冷目标仍是 0，整体 NDCG 的配对区间跨过零。因此这一轮的结论是“不替换”，不是“多兴趣更好”。均值和三个种子的标准差都不是置信区间。不同轮次的用户样本也不能直接相减，当成跨轮提升。

八、第五阶段：把算法接入可操作的系统

  • 一次推荐请求如何经过各个模块。
  • 用户收藏、屏蔽和撤销如何影响后续请求。
  • 新品如何完成校验、编码、索引构建与发布。
  • 模型、物品映射和索引如何保持版本一致。
  • 发布失败、请求超时和版本回滚如何处理。
  • 前端怎样展示真实状态与实验结果。

一次推荐现在按这个顺序走：校验会话令牌和幂等键，取得这一个请求的执行租约，绑定当时的商品包、模型身份和已见集合，再做召回、排序、过滤和 Top-K。结果与请求一起写入数据库。相同键加相同输入会重放原结果；相同键加不同输入返回 409。收藏、隐藏和撤销必须来自该会话真实返回过的商品，按 event_id 幂等，并在状态变化时推进历史版本。

新品不进入旧的 R06 权重。独立内容基线入口只需要服务环境和本地 PostgreSQL：创建临时 schema、合成目录和一个后台 worker。导入和构建不会自动发布，页面确认之后才切换活动版本。版本切换、下架和恢复会让旧的构建预览失效。回滚使用原来的发布协议，不复活已下架商品，也不改写已经返回的推荐。

冻结 R06 是另一条入口。它装载已批准的 137,249 件商品包，默认关闭，管理员在演示入口里也是关的。固定示例历史取批准包里第一个非零向量的训练商品，本包是 0060501960，不是真实用户。这个商品缺失或表示漂移时，创建和重置会话返回 409，不另选种子。结果页只展示 2026-09-17 的公开档案，并保留“多兴趣没有获得替换依据”的原文，不在页面上重新训练。

策略对比和批量评估是后台任务。评估页把已保存的比较按独立的 K 重新计算 Top-K、NDCG@10 和 Recall@20，失败指标保持未知，不补零。普通推荐账本不和这些任务混在一起。

页面必须从服务地址打开，直接用 file:// 调不到 API。公网身份、多 worker 租约续期和多机部署没有做。发布锁按实际目录表隔离；从旧的全局锁升级时，必须先停掉同一目录的 API 和各类 worker，再一起启动新代码。

九、第六阶段：性能分析与 C++ 优化

  • 如何测量排队、模型、检索和后处理耗时。
  • 实际瓶颈出现在哪里。
  • 为什么选择某个模块进行优化。
  • Python 与 C++ 的接口、数据传递和生命周期如何设计。

在线完整包是另一回事。原期限是 2 秒。目录读取和可信捕获经常占掉其中一大段；重置后的新计算曾经在这个期限上返回 504。把目录行从字典换成紧凑 tuple 后，负载验收没有通过：120 笔、并发 2 时出现几十个 recommendation_timeout。这次减配已从生产捕获路径撤回。随后把同会话不同推荐键的入场锁从 FOR UPDATE 改成 FOR SHARE，同键和反馈、重置仍排他。未插桩的 120 笔负载仍有 7 个 504，成功吞吐约 0.933 次/秒，全部客户端耗时的 p50 约 1.985 秒。计时包含每笔新建 HTTP 客户端，不等于纯服务时间。

    • 混合召回需要显式设计路由策略，单一方法无法解决所有场景。
    • 门控机制能够在不跳过检索路径的前提下动态调整召回策略，提升冷商品曝光。
    • 排序阶段的冷样本加权是补充手段，主要提升仍来自召回和粗排的覆盖范围。
