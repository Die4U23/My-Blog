EvoRec 项目介绍：动态商品库推荐、离线实验与服务闭环

2026-10-27 · 持续更新

这篇文章记录 EvoRec 如何从冷启动研究问题发展为带有离线实验和本地可操作 Demo 的项目，并区分实验结果、系统能力与尚未验证的范围。

截至 2026-10-27：R01–R06 离线研究已形成完整记录；当前本地 Demo 提供两条分开的体验路径——批准的冻结 R06 模型，以及不依赖研究模型的合成商品内容基线。它不是生产推荐服务，也不表示完整研究 PRD 已完成。

本文的早期实验数字和失败记录仍按当时协议保留。最新版本还修复了发现页、反馈来源绑定及标签页状态恢复问题；这些页面和恢复检查不能替代完整模型负载复验。当前 R06 结果仍保留 A-frozen-s17：多兴趣方案没有显示稳定优势，冷商品进入候选池略有增加，但无历史冷目标仍未命中。Demo 里的 adaptive 是兼容入口并固定解析为 dense，不是动态学习路由。

一、项目背景与目标

EvoRec 面向动态商品库的冷启动问题，将离线推荐研究、服务端请求处理和本地交互演示放在同一个项目中。关键问题不只是模型排序分数，还包括新品何时进入候选集、反馈怎样改变后续请求，以及模型与商品版本如何保持可追溯。

为什么选择推荐系统

推荐系统是一个既有理论深度又有工程复杂度的领域。它涉及机器学习、信息检索、系统设计等多个方面，同时也有明确的业务价值和评估标准。选择“动态商品库推荐”这个场景，是因为它包含了推荐系统中最核心的挑战：

  • 冷启动问题：新商品没有历史交互数据，如何快速让它们参与推荐？
  • 实时性要求：商品库不断更新，系统需要快速响应新品入库。
  • 多路召回融合：需要平衡协同过滤、内容检索等多种策略。
  • 效果可验证：有清晰的离线评估指标和在线业务指标。

项目目标

项目覆盖以下能力：

  • 召回与排序：协同过滤、内容双塔、策略门控、冷样本加权和多兴趣候选的离线实现与比较。
  • 服务与持久化：FastAPI 请求编排、PostgreSQL 请求/结果记录、反馈与商品版本管理。
  • 商品生命周期：导入校验、异步构建、预览、显式发布、下架和回滚。
  • 对照评估：固定输入与策略、分组指标、不确定性分析及结果追溯。

研究轨迹现已覆盖 R01–R06：热门与协同基线、序列模型、内容双塔、门控与冷商品保留、冷样本加权排序，以及多兴趣召回和残差排序的受控比较。系统侧也已把推荐请求、PostgreSQL 持久化、反馈、商品构建/发布、结果查看与本地页面接通。二者是不同层面的成果：离线指标回答冻结协议下的研究问题，Demo 证明本地流程可操作，不代表线上业务效果。

二、核心问题与解决思路

问题场景

考虑一个典型的电商推荐场景：每天都有新商品上架，这些新商品没有任何历史交互数据。如果使用纯协同过滤方法，这些商品永远不会被推荐给用户，因为它们不在模型的"词表"中。但对商家来说，新品的曝光至关重要；对用户来说，新品可能正是他们感兴趣的。

这就是推荐系统中的"冷启动"问题。EvoRec 项目专注于解决这个问题，同时保持整体推荐质量。

技术挑战

  • 冷商品可达性：没有交互历史的商品如何进入候选集？
  • 多路召回融合：如何平衡协同过滤（基于用户行为）和内容检索（基于商品特征）？
  • 动态策略调整：针对不同用户（新用户 vs 活跃用户），应该采用什么样的召回策略？
  • 排序优化：如何在排序阶段提升冷商品的曝光，而不损害整体效果？

系统目标

EvoRec 的最终目标是构建一个完整的可演示系统，包括：

  • 推荐服务：支持实时推荐请求，处理用户反馈（收藏、屏蔽等）。
  • 商品管理：支持新品入库、编码、索引构建和发布。
  • 策略对比：可视化展示不同策略的效果差异。
  • 效果看板：实时监控推荐质量和冷商品曝光率。

成功标准不仅是功能完成，更重要的是实验可信、结果可追溯。每个设计决策都需要有数据支撑。

三、技术选型与架构设计

技术栈选择

技术选择围绕离线实验效率、服务边界和本地可复现演示：

  • 算法框架：Python + PyTorch — 推荐算法领域的主流选择，有丰富的预训练模型和工具库。
  • 向量检索：Faiss — Facebook 开源的高性能相似度搜索库，支持多种索引类型。
  • 数据存储：PostgreSQL — 可靠的关系数据库，支持事务和复杂查询。
  • API 服务：FastAPI — 现代 Python Web 框架，自动生成文档，异步支持好。
  • 前端展示：原生 HTML/CSS/JavaScript — 当前本地 Demo 用无构建步骤页面展示推荐、反馈、商品管理与结果查看；React 等框架仍是后续选项。

架构设计原则

系统架构遵循以下原则：

  • 模块解耦：算法、数据、服务和展示模块独立开发和测试。
  • 契约优先：先定义接口和数据格式，再实现具体逻辑。
  • 版本管理：模型、编码器、索引作为一个 bundle 统一版本。
  • 可测试性：关键路径有自动化检查，使用测试替身隔离依赖。
离线研究：src/evorec/research → 候选生成 / 训练 / 评估
                              │ 固定模型与数据版本
                              ▼
浏览器 → FastAPI → Recommend.execute → PostgreSQL
                    │ 请求快照 / 资格过滤 / Top-K / 幂等结果
                    ├── 冻结 R06：CF + 内容召回 + 排序器
                    └── 新品 Demo：合成目录内容基线
后台 workers：商品目录构建 / 策略比较 / 批量评估

图中的冻结模型与合成内容基线是两条分别配置的路径；离线研究产物不会自动成为线上活动模型。

关于 C++ 的考虑

考虑到主要算法实验基于 Python，实现初期没有在性能关键路径额外引入 C++：

  • 先用 Python 验证：在明确瓶颈之前，不引入额外复杂度。
  • 保留优化空间：如果后续测量发现性能问题，可以用 pybind11 封装 C++ 扩展。
  • 利用现有工具：Faiss 本身就是 C++ 实现，通过 Python 绑定使用即可。

这一取舍减少了跨语言边界，同时保留了在测得实际瓶颈后再评估 C++ 扩展的空间。

四、工程框架搭建

设计原则

工程组织需要满足以下原则：

  • 契约先行：先定义接口和数据格式，模块之间通过契约通信。
  • 可测试性：核心逻辑独立于外部依赖，可以用测试替身验证。
  • 版本一致性：模型、编码器和索引作为一个 bundle 统一管理。
  • 清晰的状态转换：区分“服务启动”和“推荐就绪”，明确商品的生命周期。
src/evorec/domain/          领域对象、规则与协议
src/evorec/application/     推荐、反馈、商品与评估用例
src/evorec/infrastructure/ 数据库、模型与 worker 适配器
src/evorec/api/             FastAPI 路由与请求契约
src/evorec/research/        离线数据处理、训练与评估
web/                        原生 HTML/CSS/JavaScript 页面
db/                         PostgreSQL schema 与迁移
scripts/                    服务、目录、比较和评估任务入口

核心模块

  • domain/ — 领域对象和业务逻辑，不依赖具体实现。
  • infrastructure/ — PostgreSQL 与模型运行时等外部依赖适配器。
  • application/ — 应用层服务，协调领域对象和适配器。
  • api/ — FastAPI 路由和请求处理。
  • research/ — 离线实验脚本和评估代码。

当前实际进展

下列清单是 2026-09-15 初始框架阶段的记录，不是当前系统能力的完整说明。此后服务与本地 Demo 已继续落地：

  • 建立了 FastAPI 服务骨架，定义了推荐接口的输入输出契约。
  • 实现了 55 项自动检查，覆盖请求绑定、参数验证、超时处理等边界情况。
  • 使用测试替身隔离了模型和存储依赖，确保应用层逻辑可独立验证。
  • 定义了商品状态机，明确了从入库到上线的完整流程。

历史验证边界：当时的 55 项检查只支持契约和应用层边界，不证明推荐效果、数据库事务或真实吞吐。后续数据库、推荐服务与页面交互另有独立验证记录，不能把这组旧检查数当作当前回归规模。

五、离线实验档案：R01–R05

以下实验按发生顺序保留其数据、指标和当时结论。它们是历史运行，不是当前服务性能或新商品质量的证据；R06 是后续冻结比较，负责更新当前策略取舍。

  • 数据从哪里来，包含哪些字段。
  • 如何清洗交互、统一商品 ID 和处理缺失数据。
  • 如何划分训练、验证和测试数据。
  • 怎样避免未来信息进入训练或评估。
  • “模型冷物品”和“刚刚发布的新品”有什么区别。
  • 首次跑通的基线、使用的设备、资源消耗与结果。

R01 已完成。 从官方 Video_Games 交互文件读取前 50,000 条，得到 20,375 个用户和 18,508 件商品；在 2,291 个测试正反馈上，热门推荐 NDCG@10 为 0.007388，ItemCF 为 0.004636。共有 79 项检查通过，9,852 条逐请求结果完成独立核对。前缀样本中 1,101 个测试目标在请求时尚未被观察到，保留在主指标分母中。

R02 已完成。 完整扫描 4,555,500 条交互，按固定用户哈希保留约二十分之一用户的全部记录，得到 226,172 条交互和 137,103 个用户。GPU 自注意力序列模型完成 4 次训练、39 个 epoch 和三个种子运行；测试 NDCG@10 为热门 0.004755、时间衰减协同融合 0.008380、序列模型均值 0.005628 ± 0.000222。序列模型超过历史热门，但没有超过更强的时间衰减基线。

本轮还发现 6,874 个模型冷且可用目标全部未命中。没有商品表示入口时，继续增加 Transformer 训练轮数无法让新商品进入词表；下一步先补内容候选路径，并登记新的评价窗口。

R03 已完成。 引入内容双塔架构，使用商品标题、品牌和类别进行语义编码。完成 48 个 epoch 训练，构建协同过滤与内容检索的混合召回策略。内容融合改善整体排序性能，但冷商品命中率仍低于预期。

R04 历史实验。 冻结 R03 模型，预登记五种冷商品保留与门控策略，并在新用户验证集上按整体质量下限和同分规则选择配置。测试集上 seed 17 的 reserve-2 比 fixed 多命中 2 个冷目标，gated-2 没有提升；命中集合并非嵌套。因此，这组结果只说明指定策略在该次固定测试中的差异，不足以支持门控稳定提升效果的泛化结论。

R05 历史实验。 引入 ColdListMLP，对冷样本加权训练。原始同候选池对比中 ColdListMLP 仅运行 seed 17，普通 ListMLP 有三个种子；因此不能把该单种子差异概括为可重复的稳定提升。后续在独立样本上的三种子复验报告 NDCG@10 为 0.009315 ± 0.000387，冷目标命中数为 26 / 24 / 27；它验证了另一轮固定协议下的结果，并不消除不同样本或策略之间的不确定性。详见R05 三种子复验。后续 R06 的多兴趣方案配对区间跨零，当前选择仍是 A-frozen-s17。

R06 固定协议结果

R06 已完成，但没有证据支持替换原路径。 测试用户与 R01–R05 的交集为零，共 12,524 个正反馈请求、9,373 名用户。比较的是相同候选数量预算下的均值内容召回和近期多兴趣召回。验证规则保留 A-frozen-s17，本轮没有换路径。

A-frozen 均值 冻结 R05 0.010074 ± 0.000129 0.003774
B-frozen 均值 + 多兴趣 同一组冻结模型 0.010040 ± 0.000117 0.003917

冷目标进入候选池由 115 / 6,978 增至 122 / 6,978。无历史冷目标仍是 0 / 3,928。B 减 A 的整体 NDCG 差值为 −0.000033769，95% 边际区间 [−0.000260567, +0.000184014]；C 减 D 为 −0.000335551，[−0.000686012, +0.000000421]。两个区间都跨过零。测试批次里均值内容路径用时 7.865 秒，多兴趣计算另用 12.469 秒。这是离线批次时间，不是线上延迟。共 6 次训练、74 轮。50 项预登记区间按用户聚类重采样 10,000 次后独立复算，条件于固定检查点，不含训练随机性，也没有做多重比较校正。三个种子的平均不是集成推荐。数字来自仓库 README 的当前结果表。

六、推荐方法与实现

离线研究包括流行度与时间衰减协同基线、序列模型、商品内容双塔、冷商品保留/门控、冷样本加权排序，以及 R06 多兴趣召回和候选内残差排序。实验数据按时间协议切分，模型拟合与请求时可用商品资格分开处理；同一轮固定候选范围和评估输入，并分别报告整体与冷商品指标。这里的内容是项目实际实现和实验，不是论文复现目录。

R06 在独立留出用户上比较 A-frozen、B-frozen、C-adapted、D-adapted 四组方法：冷目标入池从 115/6,978 增至 122/6,978，但无历史目标仍为 0/3,928；配对区间跨零，验证规则因此保留 A-frozen-s17。它说明增加候选路径还不足以解决冷启动，也没有证据替换当前保留模型。

七、实验协议与结果

每轮实验记录样本、时间切分、随机种子、候选池和指标定义。R06 使用 12,524 个正反馈事件和 9,373 名用户，与 R01–R05 用户无交集；模型质量同时查看 NDCG@10、冷 Recall@20 与配对不确定性。种子标准差不是置信区间，配对区间跨零也不能写成方法胜出。最新研究结论和区间见R06 报告。

自适应预算路由算法、生成式推荐及更完整的研究 PRD 仍未交付；固定别名 adaptive 不应被当成这些研究功能。

八、服务与商品闭环

推荐服务由 FastAPI 与 PostgreSQL 支撑。Recommend.execute 捕获会话历史、商品资格和模型绑定的请求快照，执行召回排序、资格过滤、去重与 Top-K，再保存并返回同一版本结果；相同幂等键重放原结果，输入冲突会拒绝。反馈携带请求来源与会话 epoch。商品管理采用导入校验、后台构建、预览和显式发布分步流程，避免把导入误当成线上资格。批准的冻结 R06 包与合成商品内容基线属于两条独立路径。

页面状态隔离迟到响应并在刷新时恢复服务端可确认的状态。浏览器标签页存储异常时提示恢复风险，并在当前页面内存中保留原操作编号供重试；若刷新或关闭页面，未写入的内存状态不保证恢复。详见Web 行为说明与恢复验证记录。

九、负载诊断与性能边界

项目已对 R06 服务做过 HTTP 期限、并发、队列和结果持久化路径的诊断。2026-10-14 的历史冻结包在完整商品目录、单 worker、原 2 秒期限下，两轮并发负载各 120/120 成功且无 504，客户端 p95 约 1.87 秒；这是特定机器、包和提交上的测量，不是长期服务级别。更早出现的间歇 504 根因未全部归因，2026-10-27 版本也没有重新验收完整 R06 负载。

当前没有 C++/pybind11 扩展，也没有足够证据报告它的性能收益。300 ms、20 QPS、长期稳定性和生产级 SLA 均未验收。回归检查、网页演示和离线算法指标回答不同问题，不能互相替代。

十、项目限制与交付

截至本文更新，可交付物包括 R01–R06 离线报告与复算材料，以及能够本地启动的推荐 Demo：冻结模型路径用于反馈与策略体验，合成内容路径用于新品导入、构建和发布；比较、评估任务和结果页提供研究结果浏览。还没有被证明的是稳定服务级别、持续负载能力或真实业务收益。后续工作应继续针对这些边界补充可复核的证据，并明确新研究功能与现有能力的差别。
